# 후속 백엔드 작업: 기간 중 Bye 허용

이 문서는 수정 요청서이며, 이번 프론트 통합에서 `BOB_BE` 파일은 수정하지 않았다.

## 프론트가 보내는 요청

`PUT /api/v1/items/{item_id}/decision`

```json
{ "decision": "GIVE_UP" }
```

Bearer 인증과 기존 Idempotency-Key를 사용한다. `actual_price`, `purchased_on`은 Buy에만 보낸다. API 주소·필드명 변경은 필요 없다. 미확정 물품은 시작 전/진행 중/연장 중에도 Buy·Bye 버튼을 표시하고, 보류는 기간 종료 후에만 표시한다.

## 현재 차단 조건과 변경 범위

`app/api/core.py`의 `decide_item`에서 현재 `body.decision != "BUY" and today < simulation.end_date`이면 `409 SIMULATION_NOT_COMPLETE`를 반환한다.

이를 **기간 종료 전 HOLD만 차단**하도록 바꿔 GIVE_UP을 허용해야 한다. 기존 소유자 검사, row lock, 확정된 BUY/GIVE_UP의 재결정 금지, 구매 정보 검증은 유지한다. HOLD의 기간·마감일·멱등 처리도 유지한다.

## 조기 포기의 저장·조회 처리

- 성공 시 `item.decision=GIVE_UP`, `item.decided_on=오늘`로 확정한다. 기존 GIVE_UP 경로처럼 물품 가격을 가상 저축 이벤트로 한 번 적립하고 목표 달성 여부를 갱신한다. 실제 지출·구매·구매 후 점검은 만들지 않는다.
- 반복/동시 요청에서 가상 적립이 중복되지 않아야 한다. 같은 GIVE_UP 재시도는 기존 확정 결과를 반환하고 BUY/HOLD로 변경하려는 요청은 기존처럼 거부한다.
- 기존 질문·답변을 삭제하지 않는다. 오늘 질문, 결정 대기 목록, 앞으로의 질문/알림 대상에서는 제외한다. 홈의 진행 중 목록에서는 빠지지만 `GET /items` 전체 기록에는 남겨야 한다.
- 예정된 미래 관찰일이 시간이 지나면서 미응답으로 늘어나지 않도록 조기 포기의 관찰 종료 기준을 저장하거나 `decided_on`에서 일관되게 계산한다. 조기 포기 시 pending days는 0으로 처리한다.
- **`ended_early_on`만 설정하면 안 된다.** 현재 `app/services/simulations.py`는 이 필드가 있으면 무조건 `EARLY_PURCHASED`로 표시하며, `local_questions.py`와 `pre_purchase_questions.py`도 `EARLY_PURCHASE`로 해석한다. 조기 구매와 조기 포기를 구분하도록 상태·비교 사유 처리 및 필요한 스키마를 함께 정리한다. 새 코드명을 도입한다면 `EARLY_GIVE_UP` 등으로 명확히 구분한다.
- LOCAL 질문은 답변이 기기에 있으므로 조기 포기 요청만으로 서버가 답변 수를 알 수는 없다. 종료일·포기 상태와 기기 기록을 보존하고, 미전송 답변을 추정하거나 기간 미완료를 정상 완료 통계로 계산하지 않는다. 기존 조기 구매와 동일하게 결과 비교 대상에서 제외하는 것이 안전하다.
- 포기 횟수·구매 이유별 포기율·가상 적립 통계에는 정상 반영하되, 구매 후 실제 사용 비교 대상으로 만들지 않는다.

## 검증할 시나리오

1. 등록 당일(시작 전), 진행 첫날/중간날, HOLD 연장 기간, 정상 종료 후 GIVE_UP이 각각 성공한다.
2. 종료 전 HOLD는 계속 409이고, 조기 BUY와 정상 구매 처리는 기존대로 작동한다.
3. 같은 GIVE_UP 요청을 재전송·동시 전송해도 SavingEvent와 목표 적립은 한 번이다.
4. 확정 후 다른 결정은 409이며, 다른 계정의 물품은 접근할 수 없다.
5. 포기 이후 `/today`, 홈, 질문 생성, 알림 대상에서 제외되고 전체 기록에서 조회된다.
6. 날짜를 며칠 이동해도 조기 포기 후 미응답/pending 수가 증가하지 않고 상태가 조기 구매로 표시되지 않는다.
7. 지출·Purchase·후속 점검이 생기지 않으며 목표·리포트 값은 한 번만 반영된다.
8. 수정 서버에서 Expo의 기간 중 Bye → 확정 → 홈 → 전체 기록 → 앱 재실행 흐름을 확인한다.

프론트는 현재 서버의 409 응답을 받으면 오류를 표시하고 기존 물품·기기 답변을 유지한다. 백엔드 변경 후 성공 응답을 받으면 같은 코드로 서버 홈을 다시 조회한다.
